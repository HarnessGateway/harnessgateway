Every coding agent, one API.

HarnessGateway speaks the OpenAI Responses API and nothing else. Behind it, a harness package your organization owns maps each request onto a coding-agent CLI, or any command line, running in a sandbox with your provider keys, your instructions and your tools. Switch harnesses by changing the model name.

How it works

A request comes in as a Responses call. The platform reads the model name to pick the harness and the provider, then hands the whole request to the package. The package drives the CLI and emits Responses events. Nothing in between invents a schema.

1Set up a provider

Anthropic, OpenAI, DeepSeek or any compatible endpoint. The key is stored encrypted and injected into the sandbox for the length of one turn, behind a door that only reaches the hosts the package lists.

2Pick or build a harness

Fork a catalog package or write your own: a git repository with harness.json, install.sh, request.sh and the seeds the CLI expects in its workspace and home. Edit it in the console, commit, push from the CLI.

3Call it like any model

Point the OpenAI SDK at the gateway with model: "codex" or "claude-code/anthropic/claude-sonnet-4-5". Stream, continue with previous_response_id, run in the background, steer or cancel.

# the official SDK, any language from openai import OpenAI client = OpenAI(base_url="https://hg.example.com/v1", api_key="hg_...") r = client.responses.create(model="codex", instructions="Keep patches small.", input="Add a --dry-run flag to bin/deploy", stream=True) for event in r: print(event.type) # response.output_item.added, response.output_text.delta, ... response.completed

Twelve packages, verified

Each catalog package was run against a live provider on the day it shipped: a first turn that writes a file, a second turn that recalls it, and a streamed turn. The checks are recorded in the package and shown in the console.

What the platform owns

The package owns how the CLI is run. The platform owns everything an organization should not have to build twice.

Managed sandboxing

Every turn runs in a fresh container as the organization's own uid, read-only root, no capabilities, a private network with a single door. The tenant controls the egress list and nothing else about the sandbox.

Keys injected per request

Provider keys never reach the package or the CLI. The sandbox sees a per-turn token; the door swaps it for the real key on the way out and only to the provider's host.

Traced end to end

The request as sent, the events as emitted, the response as returned, the package's log and the door's log: one trace per turn, in the console and over the API.

Workspaces that persist

A conversation keeps its workspace and the CLI's state across turns. Browse the files, read the trace, steer the run with a message mid-turn, or cancel it.

Organizations and teams

Owners manage providers, members and keys. Teams own harnesses only their members use. Sessions are visible to their creator and the owners.

Packages as git

A harness is a repository the platform hosts. Commit from the editor, push from the CLI, fork from the catalog or from a teammate, read the history, export a bundle.

Any CLI

The platform executes command lines; coding agents are the ones it ships packages for. The shell package runs the request as a script with no provider at all. Wrap yours the same way.

Metered, not tokened

Compute, egress and storage are what the platform meters; tokens stay between you and your provider. Usage per organization, team, member, harness and session.

Built for agents too

Idempotency keys for safe retries, a 429 with Retry-After at the ceiling, background turns, and signed webhooks that deliver the final response.

Rodeo

Run one task across several harnesses at once, watch them stream side by side in their own workspaces, and pick the winner. The picks accumulate into a leaderboard for your organization, on your tasks, with your providers.

Deploy in one command

One container, one data directory, Docker for the sandboxes. The compose file brings Postgres, S3-compatible storage and nodes that join. The managed platform runs the same image.

# one box docker run -d --name harnessgateway -p 8000:8000 \ -v hg:/data -v /var/run/docker.sock:/var/run/docker.sock \ -e HG_PUBLIC_URL=https://hg.example.com ghcr.io/harnessgateway/harnessgateway:8 # or Postgres, S3 and nodes, with the compose file in deploy/ docker compose -f deploy/compose.yml up -d && docker compose -f deploy/compose.yml run --rm api doctor
