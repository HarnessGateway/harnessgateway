Every coding agent, one API.

HarnessGateway speaks the OpenAI Responses API and nothing else. Behind it, a harness package your organization owns maps each request onto a coding-agent CLI, or any command line, running in a sandbox with your provider keys, your instructions and your tools. Switch harnesses by changing the model name.

How it works

A request comes in as a Responses call. The platform reads the model name to pick the harness and the provider, then hands the whole request to the package. The package drives the CLI and emits Responses events. Nothing in between invents a schema.

1Add a provider

Anthropic, OpenAI, DeepSeek or any compatible endpoint. The key is sealed on arrival and swapped in at the gateway for one request at a time; no sandbox ever sees it.

2Add a harness

Fork a catalog package or upload your own: harness.json, install.sh, request.sh and the seeds the CLI expects. A git repository the platform hosts, with a history.

3Start a session

In the app, or from any OpenAI SDK with model: "codex". Type, press Enter. A message sent while the agent works stops it and runs the new message on the same workspace, like a coding agent's web view.

# the official SDK, any language from openai import OpenAI client = OpenAI(base_url="https://hg.example.com/v1", api_key="hg_...") r = client.responses.create(model="codex", instructions="Keep patches small.", input="Add a --dry-run flag to bin/deploy", stream=True) for event in r: print(event.type) # response.output_item.added, response.output_text.delta, ... response.completed

Twelve packages, verified

Each catalog package was run against a live provider on the day it shipped: a first turn that writes a file, a second turn that recalls it, and a streamed turn. The checks are recorded in the package.

Where a CLI cannot do something yet (resume a session headlessly, stream its events) the package says so, and the response carries the fallback honestly instead of pretending.

What the platform owns

The package owns how the CLI is run. The platform owns everything an organization should not have to build twice.

Multi-tenant sandboxing

Every turn runs in a fresh container as the organization's own uid, read-only root, no capabilities, a private network with a single door. The tenant controls the egress list and nothing else about the sandbox.

Keys swapped per request

Provider keys never reach the package or the CLI. The sandbox sees a per-turn token; the gateway swaps it for the real key on the way out and only to the provider's host.

Sessions that persist

A session keeps its workspace and the CLI's state across turns, on whichever node runs the next one. Continue it from the app or with previous_response_id from any client: it is the same session.

Traced end to end

The request as sent, the events as emitted, the response as returned, the package's log, the provider exchanges: one record per turn, over the API.

Organizations

Owners manage providers, harnesses, members and keys; members run sessions and see their own. Sign up with an email, or let the deployer create organizations and invite people.

Any CLI

The platform executes command lines; coding agents are the ones it ships packages for. The shell package runs the request as a script with no provider at all. Wrap yours the same way.

Deploy in one command

One container, one data directory, Docker for the sandboxes. The compose file brings Postgres, S3-compatible storage and nodes that join. The managed platform runs the same image with other names in its environment.

# one box docker run -d --name harnessgateway -p 8000:8000 \ -v hg:/data -v /var/run/docker.sock:/var/run/docker.sock \ -e HG_PUBLIC_URL=https://hg.example.com ghcr.io/harnessgateway/harnessgateway:9 # or Postgres, S3 and nodes, with the compose file in deploy/ docker compose -f deploy/compose.yml up -d && docker compose -f deploy/compose.yml run --rm api doctor
